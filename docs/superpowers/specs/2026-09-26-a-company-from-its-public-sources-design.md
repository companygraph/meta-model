# A company is drawn from what it publishes

A company arrives as a web address and leaves as an instance the model can hold: its identity, the sources its facts are mastered in, its products and the domains they sit in, its vision and values where it publishes them, the questions its site answers, and a thin profile for each person its team page names that the operator chose to keep. The tooling gains a skill for that work, `companygraph-company`, beside `companygraph-profile`, and a smaller skill both of them call, `companygraph-consent`, which finds the terms a source publishes under, asks whether a consent is needed, takes the consent the operator gives, and keeps it on the source every fact names. Most of the work is judgment, which page says what the company is, which of three names is the one it writes, whether a person on a team page wants to be in a model, so both are procedures, and the operator is asked wherever the answer is theirs.

Status: decided by the owner on September 26, 2026, on seven recommendations put to them in one message and taken as a whole. The skill is named for its result, as the four existing skills are. It runs inside an instance `init` has written and asks Create or Update. Its research ends in one ledger file and one round of questions rather than either alone. A consent lives on the source, as prose, with no core change. Consent is its own skill rather than a paragraph two skills share. LinkedIn is read only as the operator pastes it or as its public page loads without a login. And the consent the profile skill asks for is the person's, the consent the company skill asks for is the company's, whereas the terms a source publishes under are the operator's to check in either case.

## Where this comes from

`companygraph-profile` did this for a person in September 2026: a folder of documents becomes a profile, its experiences and the vocabularies they name, with the judgments put to the operator and nothing committed. Its first run, on the reference instance, changed it in three places, and the pull request that shipped it says which. Three company instances were built by hand in the same month, one describing the tooling, one describing a project, one describing a company of one, and each began the same way: read what the company already says about itself, on its site and its repositories, and put that into the types core has. The reading was the same each time and was never written down.

The site is where a company states what it is. Its imprint carries the legal name, the seat and the contact address, the about page says what it does and for whom, the products page names what it ships, a values or mission page says what it holds to and where it is going, an FAQ answers what visitors ask, and a team page names the people. A GitHub organization adds a README, the pinned repositories and a license beside each. A register entry confirms the legal name and the seat. Everything core asks for on the first day of an instance is public for most companies, and the skill is the reading of it as a procedure.

What that reading must not do is also known. A person on a team page is personal data, and a model that is served over MCP and drawn on a site is a publication of it. A company's statements are its own, and restating them in a model somebody else publishes is a use the company may or may not have agreed to. A repository's README is under its license, a site's text under its terms, and a platform's page under that platform's agreement, which for LinkedIn forbids automated reading. None of the four skills asked any of this, and the profile skill reads private documents whose holder is presumed to have handed them over for the purpose. The consent skill is where the question is asked once and its answer kept.

## The company skill

`companygraph-company` is a procedure under `agents/claude/skills/`, so `init` writes it and `upgrade` moves it. It reads `<units>/core/CONVENTIONS.md` whole and each type's schema whole before writing an entity of it, and the instance's own agent file for what the instance has decided, exactly as the profile skill says it. Every type's schema is the contract and the skill restates none of it.

1. **Create or Update.** Ask which. Create is an instance `init` wrote whose identity is still the stub, its H1 the instance's name and its tagline placeholder prose. Update is an instance with content, and the run reconciles before it writes.

2. **The address.** Ask for the company's web address. It is the one question the run needs; everything else follows from it. Fetch the front page and read the imprint, the legal page or the about page for the name the company writes, its seat and its contact address, and confirm the name with the operator before anything else, because it is the identity's H1 and every later fact is about it.

3. **Research.** Read the site's pages reachable from its navigation and footer: about, team, products or services, values or mission, careers, FAQ, imprint, press, and the index of a blog but not its posts, which document an experience and belong to a profile. Honor `robots.txt`: a path it disallows is not read, and the ledger says so. Find the GitHub organization by the site's link to it or by the company's name, and read the organization profile, the pinned repositories, each one's README and the license beside it. Read LinkedIn only as the public company page loads without a login, or as the operator pastes it, and never through a session, because its agreement forbids the rest. Search the web for the company's name with its domain and note what the search surfaces without reading it yet: a register entry, a Crunchbase or Wikipedia page, press, a podcast. Every page read is written to the ledger with its address and the date it was read.

   Take out only what a schema has a place for: the name, the tagline as the company writes it, what it does and for whom, its seat and contact address, each presence it maintains elsewhere, each product and what it is, each feature where the site names one, the areas the site groups its offer into, its vision or mission where stated, each value where stated, each question its FAQ answers, and for each person on a team page the name, what the page says the person does, and the person's own public presences. A revenue, a headcount, a funding round, a founding year stated as an age, a customer count: these are numbers that move, no schema holds them, and they are not extracted and not noted anywhere. A brand is left to the owner: what the mark means and how the voice sounds is not readable from outside, and the stub `init` wrote stays until the company writes it.

4. **The ledger.** Write `dist/research/<date>-<instance>.md`, one table per type, one row per entity or fact the run proposes, with the address it came from and the words the source uses. Below the tables, three lists: the further sources the search surfaced and the run did not read; the pages read that yielded nothing; the pages not read and why, a robots rule, a login, a paywall. `dist/` is gitignored, so the ledger is the operator's record of the run and never part of the model; what the model keeps is the source each fact names.

5. **The operator decides.** Show the ledger. For each type, the operator keeps, strikes or renames each row, as the profile skill lets them strike a list before anything is written. Then ask which of the further sources to read; on any yes, return to step 3 for those alone and add to the ledger, and stop when a round adds nothing the operator keeps. A team page is a special case of the first question: each person is a row the operator keeps or strikes by name, and a struck person is not mentioned in the model anywhere.

6. **Terms and consent.** For every source the kept rows name, run `companygraph-consent` with the company as the subject, and with each kept person as a subject of their own. What it writes, and what a declined consent does to the rows that rested on it, is that skill's to say. The run does not write an entity whose consent was declined.

7. **Reuse before creating.** Read the instance's agent file for facts the owner has decided to leave out of the model and treat each as settled. List the H1s already in every type folder the kept rows would write to. On Update, read every entity the rows would touch and hold each kept fact against it: already held, and where; new; held differently, with both versions quoted; or left out by a recorded decision. Show that reconciliation before writing, because on a model that is already rich most of a site is already held.

8. **Write.** Sources first, one per place the kept facts were read from, each with its `url`, its description saying what it holds and that nothing syncs from it, and the sentences the consent skill wrote. Then the identity: the H1, the tagline as a draft in the company's voice, `## What it is`, `url`, `location` and `email` where the imprint gives them, and one `## Also at` row per presence the operator kept. Domains before products and products before features, because each names the one before it. Vision and values only where the company states them in its own words, and the schema's writing rules hold: a value's `## In practice` is drafted from what the site says following it looks like, and shown as a draft. Questions last, since a question rests on entities that must exist. Each kept person becomes a profile with `nature` human, a tagline drafted from what the page says, the person's `## Also at` rows, and no `## Skills` table: a public page evidences no claim at any level, and a fuller profile is the profile skill's work from the person's own documents. The model is written in its own words with the source named; a sentence carried verbatim, a tagline, a mission line, a value statement, is carried only where the terms or a consent allow it, and the report says which sentences those are.

9. **Validate.** Run the mechanical checks, `companygraph check` or the checker at the release the instance's workflow names, then `companygraph-validate` for the writing rules no script reads. Repair what they find; where a repair would change something the operator decided, ask.

The report is the profile skill's, adapted: what was created, one line per file; what was reused, by H1; every page read and every page not read, with why; every question the operator answered and the answer; every fact left out because no schema holds it, named by kind and never by value; the consents recorded, by source; the gaps validation reported. Where the operator declined a fact the site states and the agent file does not record that decision, the line that would record it is proposed. Nothing is committed.

Two things the skill is not. It is not a crawler: it reads the pages a person would read to learn what a company is, and a blog's posts, a documentation site and a repository's code are not among them. And it does not write surfaces. A surface is a place the company publishes from the model, and a company's site is that only when the company runs the model; for an operator modeling another company, the site is a source, the place the company's own statements are mastered, and the identity's `url` is where it is. An instance whose owner is the company adds the site as a surface by hand, as the three existing instances did.

## The consent skill

`companygraph-consent` is a procedure that runs for one source and one or more subjects: a company whose statements are drawn from that source, a person drawn from it, a document read from it. It runs as a step of the company skill and of the profile skill, and it runs alone when a source is added to an instance later. It records what the operator decided and where the terms were found. It gives no legal advice, and its report says so in one line.

1. **The terms.** Find what the content is published under: a `LICENSE` beside a repository, a site's terms or legal page, a platform's user agreement, a document's own notice. Record which was found and its address, or that none was found. Name the uses the run makes of the content, and there are three: facts restated in the model's own words with the source named; text carried verbatim; a file copied, an image or a document. Say for each use whether the terms found allow it. Where the terms are silent, or none were found, the operator judges, and the judgment is written down as theirs.

2. **Is a consent needed?** Propose an answer the operator can override, from three defaults. A person drawn from any source: yes, the person's own, because a profile is personal data in a model that is published. A company drawn by an operator who is not the company: yes, the company's, because its statements are being held and republished elsewhere. A company modeling itself, or a person modeling themselves: no, and the step is one line in the report. The operator decides.

3. **Is it given?** Where a consent is needed, ask whether it has been given: by whom, in what capacity, on what date, and how, a mail, a signed letter, in person. The skill takes what the operator states and infers nothing: a consent the operator cannot state is not given. A consent not given means the content that rested on it is not used, the report names what was left out, and the instance's agent file gets a proposed line recording the decision so the next run does not ask again.

4. **Write.** The source's `> [Description]` gains one sentence for the terms and one per consent, in this form: "Published under the site's terms, read on September 26, 2026. Jane Doe, its founder, consented on September 26, 2026, by mail, to its statements being held in this model." The source is in the model, committed and versioned, so the record is kept the way every other fact is, and it sits on the one entity every fact names.

The record is prose on the source rather than fields on its schema, which was the decision. A source in a company of one carries at most one such sentence, and a source in a small company a handful. An instance whose sources come to hold many, a company with a large team each of whom consented, is the case that asks for a `## Consents` table on the source schema, with `Who`, `For`, `Given` and `How` as columns of strings, and that is a core change of its own once an instance asks for it. Until then the sentence is the form, and the skill writes it in one shape so a later move to a table is a mechanical one.

## The profile skill's change

`companygraph-profile` gains one step between its **Reuse before creating** and **Write the vocabularies first**: **Terms and consent**, which runs `companygraph-consent` for the source the profile will name, with the person as the subject and the documents as what is drawn. For the owner of a company of one modeling themselves it is one line in the report. For a person other than the owner it asks for the person's consent before anything about them is written, and a consent not given ends the run with nothing written, as a wrong person does in its **Confirm the person** step. The steps after it renumber, and nothing else in the skill changes.

## What was left out

A `license` and a `consent` field on the source schema: a core change, and the prose form serves the instances that exist. The table form is named above as the change to make when a source holds many.

Reading LinkedIn through a session, or any page behind a login: the platform's agreement forbids it, and the skill says so in the ledger rather than doing it.

Surfaces: explained above. A site is a source unless the company runs the model.

Brand: not readable from outside as meaning, and the type's spec says the values are not in the model either. The stub stays for the owner.

Numbers: a revenue, a headcount, a funding round. No schema holds them, they move, and R17 says a stated number the model does not master is the drift the model exists to end.

Skills, levels and evidence for a person drawn from a team page: a public page shows that a person holds a seat, not what they can do at what level. The profile skill, from the person's own documents, is where a claim is earned.

Experiences: a company's history is a profile's experience, and the skill writes no profile with experiences. A press page and a blog are noted as further sources for a later profile run, not read.

## The tooling

Two folders are new, `agents/claude/skills/companygraph-company/SKILL.md` and `agents/claude/skills/companygraph-consent/SKILL.md`, each with the frontmatter the four existing skills carry, `name`, `description` and `allowed-tools`. `init` collects the skills by walking `agents/claude/skills`, so both are written and moved by upgrade with no change to the plan. Four places name the skills by name and each gains the two: the line `init` prints, the paragraph `AGENTS.md` carries in `lib/instance-files.mjs`, the README's paragraph on `init`, and the CLI test that asserts which skills a fresh instance holds. `companygraph-profile/SKILL.md` gains its step. Core does not change and stays at 0.42.0. The package moves by a minor, to 0.49.0, and the instance workflow's `ref:` with it in the same commit, as the 0.46.1 guard requires.

The release notes say: `init` and `upgrade` now write six skills; `companygraph-company` builds an instance from a company's web address, `companygraph-consent` records the terms and consents a source's content is used under, and `companygraph-profile` asks for the person's consent before it writes.

## The first run

The profile skill was changed by its first run, and this one will be. The first run is on a fresh instance, `init` written, for a company the owner names, and the run is made by the owner at the keyboard, because every step that matters asks them something. What the run changes in the skill is committed with it, and the pull request says which steps the run changed, as the profile skill's did. Whether the instance the run produced is kept, and where, is the owner's decision at the end of the run and is not made here. The three existing instances take the skills by upgrading and are not re-run: their identities, sources and products were written by hand against the same schemas, and a second pass would find them held.

## Out of scope

A crawler, a sync from a source, a scheduled re-read that reports drift between the site and the model; a `## Consents` table on the source schema; a consent for the reading rather than the use; a consent that expires; a page on any site that lists an instance's consents; a re-run of the three existing instances. Each is a change of its own once something asks for it.
